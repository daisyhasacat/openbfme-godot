# RW 0x807A81 — command-button help content (S-2702)

## Provenance and ownership

Recovered with Ghidra 12.1.2 from the privately supplied image. **Its `stxt*`,
`.mackt`, and `.danetta` sections are modified; no independently verified clean
2.01 checksum is available.** These are findings about that image, not an
unqualified clean-retail parity claim. No binary or raw analysis artifacts are
included here.

The map resolves this to BFME2 `OldSchoolHelpBoxContentSource::createContent`,
0x805E3D (tier B, changed). The provider's virtual slot 3 creates
`InGameCommandButtonHelp`; the help manager's content-request path calls it
after control-bar hover supplies the command button. Provider +0xC is the
button. The first selected drawable supplies the selected object; its controller
is the cost player, or the local player when there is no object. The local
player remains separate for affordability and disabled-science checks.

Relevant button fields: +0x14 command, +0x20 template, +0x24 upgrade,
+0x44 special power, +0xA4/+0xA8 science vector, +0xC0 resolved revival index.
The engine carries the resolved index in `ControlBarButton::reviveIndex`.

## Recovered branches

* **RW 0x807B5D:** one science selects itself. Multiple PURCHASE_SCIENCE
  entries pick the first not owned by the cost player, retaining the final
  entry when all are owned or the player is null. Other multi-science commands
  mark the science locked, suppressing ScienceCost (the selected value has no
  subsequent consumer while locked). ScienceCost is not restricted to
  PURCHASE_SCIENCE for a single-science command. Template/upgrade branches
  precede it.
* **RW 0x807C2E:** self-repair calls the selected object's rebuild interface
  slot 12, `GettingBuiltBehavior::rebuildCost` (RW 0x85657E). The resulting
  float is truncated, not rounded up, for display. RW 0x68DAE6 is the mapped
  `Object::rva0028D491`: any KindOf bit 62, 63, 64, 65, or 135 (FS_POWER,
  FS_FACTORY, FS_BASE_DEFENSE, FS_TECHNOLOGY, FS_CASH_PRODUCER; DEVPORT-3C
  correction: these are not walls). Those objects show the cost only at zero
  health; other objects show it unless their health fraction equals one. The
  same gate applies to neighborhood repair (RW 0x807C5B is shared by both
  commands). This does not change affordability's
  separate ceiling operation or simulation timing.
* **RW 0x807CC0:** SPELL_BOOK obtains the power's required-science list,
  visits the first science OWNED by the LOCAL player, then stops. A valid
  science that is disabled (0x6AC25F) or hidden (0x6AC287) replaces the
  description with `TOOLTIP:ScienceDisabled`. The root-prerequisite check
  (0x5FF4D7) reaches memo helper 0x5FF323, whose first action returns TRUE for
  an already-owned science without examining prerequisites, so it cannot
  disable this help. Not owning a science alone does not do so.
* **RW 0x8083D1:** REVIVE resolves the record at Player +0x758. Record +0xB0
  chooses recruit versus revive labels. Template +0x48/+0x50 hold localized
  ReviveText/RecruitText (label fields +0x44/+0x4C, parser 0x73D3E0).
  Missing custom text uses the corresponding generic tooltip. Name formatting
  uses the saved Create-a-Hero name (0x80774E -> 0x61B2DF); otherwise the
  template's label +0x60 (`Hotkey` in the ThingTemplate field table RW
  0xDA3E38; DEVPORT-3C correction: `DisplayNameInvisibleForEnemy` is +0x5C;
  accessor 0x73C644), falling back to the localized DisplayName +0x30. Append newline
  and `APT:RankLabel` from record +0xC. Cost calls `PlayerHeroList::costAt`
  (0x780AD3) with the producer; positive template CommandPoints +0x628 get
  their own line. A missing record/template exits without a hero cost.
* **RW 0x808654:** CASTLE_UNPACK finds CastleBehavior (0x797AC1), requires
  `canUnpack(false)` (0x7983E3), and formats `unpackCost(player)` (0x7995FB).
  The timer does not gate the help price; module state/instant-build still do.
* **RW 0x808680:** SPECIAL_POWER resolves the template's final override and
  formats nonzero +0x80 with `TOOLTIP:UnitCost`, not `TOOLTIP:Cost`. No selected
  object or special-power module is required for this template-only branch.
* Existing ordinary build/free, command-points, prerequisites/BuildDisabled,
  and upgrade branches retain precedence. Final construction passes name,
  cost, command-points, description and faction suffix to the help renderer.

Readable reconstruction of the newly ported decisions (names from mapped
classes; local variable names descriptive):

```cpp
// RW 0x807B5D / 0x8083A2
ScienceType science = SCIENCE_INVALID;
bool locked = sciences.size() > 1 && command != PURCHASE_SCIENCE;
for (ScienceType candidate : sciences) {
    science = candidate;
    if (locked || (player && !player->hasScience(candidate))) break;
}
// After template and upgrade precedence:
if (science != SCIENCE_INVALID && !locked)
    cost = format("TOOLTIP:ScienceCost", scienceCost(science));
// RW 0x8083D1: otherwise REVIVE selects record/template, name, description,
// rank and PlayerHeroList::costAt(index, producer) as described above.
// RW 0x808654 / 0x808680
else if (command == CASTLE_UNPACK && castle && castle->canUnpack(false))
    cost = format("TOOLTIP:Cost", castle->unpackCost(player));
else if (command == SPECIAL_POWER && power && power->m_unitCost != 0)
    cost = format("TOOLTIP:UnitCost", power->m_unitCost);
```

## Follow-up recovery: repair and upgrade providers

Neighborhood repair uses rebuild-interface slot 20, RW 0x857074, mapped to
`GettingBuiltBehavior::rva00453FE7`. It requires Object +0x458 bit 0
(effectively dead), visits the source then increasing IDs then decreasing IDs,
stopping at the first missing, non-equivalent, or live object. Eligible members
contribute slot-12 costs with a float store after each sum. Eligibility is
slot 8, RW 0x856501: construction-state slot 6, module-data +0x20 SpawnTimer
branch, recent-damage query 0x68C933, health/damage state, and 0x8561C0 keep
state. **Correction:** 0x68C933 is not a nearby-builder query. Its seconds
argument is `TimeAfterDamageUntilRepairAllowed` (GlobalData +0xA88), not a
hard-coded four. For nonnegative SpawnTimer the body must be RUBBLE; otherwise
recent damage or health fraction >= 1 blocks. These queries and the contiguous
dead-equivalent sum are now ported. An unsupported HordeContain damage provider
raises an explicit error rather than silently using the individual body.

RW 0x8561C0 reads CastleMemberBehavior +0x14 as the **keep**, not a plot's
occupant. RW 0x79A09D returns unavailable for a missing/dead keep or model bits
219, 218, 69 or 62 (BASE_BUILD, JUST_BUILT, ACTIVELY_BEING_CONSTRUCTED, DYING:
the flags start at Object +0x10C, not +0x110; DEVPORT-3C correction of the
original 187 / 186 / 37 / 30). Member byte +0x24 exempts the keep itself: the constructor
clears it and RW 0x79ACED sets it while recording the keep's own ID at +0x14.
The port derives this exemption from the keep identity already represented.
The corrected shared `castleBlocks` query can change castle repair timing.

Upgrade help now uses the full affected-upgrade gate (0x694914): an attached
horde's upgrade, the completed-object filter (0x7A075A), or the alternate
non-structure/non-projectile/non-IGNORE_FOR_VICTORY filter (0x7A089B, with the
owner as the relationship context). Construction conditions are model bits
67/68 (AWAITING_CONSTRUCTION / PARTIALLY_CONSTRUCTED: Object +0x114 bits 3 / 4
with the flags at +0x10C; DEVPORT-3C correction of the original 35/36), not
object-status substitutes. The existing module and contained-object
queries follow that gate. This shared availability correction may change which
upgrade commands are accepted.

RW 0x8077D1 skips unresolved/null entries, implements ALL/ANY, and asks the
selected object's owner for PLAYER upgrades and the object for OBJECT upgrades.
Empty ALL succeeds; empty ANY fails. The composer now applies default/custom
LacksPrerequisite, HasConflictingUpgrade and AlreadyUpgraded labels with retail
precedence. Multi-selection means all selected objects own the upgrade, or none
can apply it; the live HUD passes the complete selection, not just its first ID.
Prices remain visible for prerequisite/conflict descriptions and disappear for
already-owned upgrades.

## Follow-up recovery: S-207 prerequisite requirements

ThingTemplate now owns typed `ProductionPrerequisite` records while
`ThingFactory` continues to retain the source blocks as raw diagnostic lines.
The INI field parser makes one record per `Science` or `PlayerUpgrade` row and
one per `Object` row; an object's first token is required and following
tokens are `OR_WITH_PREV`. Science names and player-upgrade names resolve
through their stores during parse, with unknown names rejected. Unit names
resolve at query time to allow forward template references; unknown units then
fail explicitly. A `CREATE_OVERRIDES` Prerequisites block clears inherited raw
and typed records before appending its rows.

The query caps unit entries at 32, counts objects controlled by the queried
player that are equivalent to the prerequisite template, excludes objects
under construction, includes effectively dead objects, and counts each object
only against the first matching entry. Adjacent OR entries fold their counts;
satisfaction requires every science, PLAYER-type completed upgrade, and
unconsumed unit group. `playerCanBuild` evaluates every typed record with
AND semantics after the existing allowed/buildable gates.

Missing requirements use localized DisplayName values, the final two missing
alternatives around `CONTROLBAR:OrRequirement`, and the retail science/upgrade
labels. Help uses the supplied selected object's player (not the local player)
for requirements, joins nonempty prerequisite descriptions with `", "`, and
places `CONTROLBAR:Requirements` after any existing description. The donor's
newline placement quirk in science/upgrade branches is retained. Since
`playerCanBuild` is also queried by production/build logic, applying previously
unsupported prerequisites can change simulation outcomes for templates that
define them; retail templates do not currently contain such blocks.

## Follow-up recovery: S-207 module-offered templates

The registry's `SpawnUnitBehavior` create proc RW 0x6506C0 calls constructor
RW 0x8BC924. Its behavior vtable at RW 0xC6FDE8 has slot 0x2C pointing to
RW 0x8A18E0, which adjusts the behavior subobject (+0x0C) to the module's
offer interface (+0x20). That interface's first slot is RW 0x8BC992: copy
the string at ModuleData +0x08. The field table RW 0xC6FEF0, registered by
RW 0x8BC981, names it **UnitName**, not the neighboring class's RequiredObject.
The same table maps UnitCommand to +0x0C and SpawnOnce to +0x1C;
constructor RW 0x65573A initializes both strings empty and SpawnOnce false.
The matching donor getter is `Common/Rva004B8732Getter.cpp` in Open-BFME-2;
the target registry, constructor, table and vtable establish the class identity.

RW 0x794F38 rejects a null template with build index -1. For a non-null
template, RW 0x794F69 scans behavior modules in order and compares each
provider's returned string exactly and case-sensitively with the template's
name (+0x64). A match returns true immediately, before command-set lookup,
the revival-index path, player build permission, upgrades or prerequisites.
There is no template-equivalence, SpawnOnce or UnitCommand check here.
Nonmatches retain the existing command-button/revival checks. The caller's
earlier factory-disabled guards and later money/queue/command-point limits
remain in force.

The port adds the optional behavior interface, typed SpawnUnitBehavior data
and the exact-name provider. Its separate automatic-production update
RW 0x8BC9B0 is not part of this query closure: the instance still reports
`isUnported()`, the factory lists it unported, and its update remains asleep
under S-140. No automatic-spawn behavior is silently claimed implemented.
The direct player-visible regression is the Goblin citadel's Fire Drake:
ObjectCreationUpgrade can now queue the template offered by this provider
even though no UNIT_BUILD button offers it (S-2009).

Tests use the real fortress module plus data-only child templates to cover
exact names rather than EquivalentTo, later modules in the list, absent
command sets, non-null-template revival precedence, and player build-gate
bypass at this query only. The existing FACT-C castle-button test now requires
the Fire Drake to be produced instead of pinning its known failure.
This can change production outcomes and simulation hashes; no pinned vectors
are changed. All addresses retain the supplied-modified-image caveat above.

## Follow-up recovery: HordeContain recent damage

`Object::rva0028C264` (donor `Object.cpp`, RW 0x68C933) is already represented by
`emotionAttackedWithin`: multiply seconds by five, ask the object's contain
module for its HordeContain interface first, otherwise consult the body's
last-damage frame and attacker. The construction and repair queries now reuse
that provider instead of bypassing it or rejecting every HORDE object.

`HordeContain::rva0046BB6F` (donor `HordeContainIface11CSlots.cpp`, RW 0x86EE52)
sets the output ID to zero and rejects `frames >= currentFrame`. It then checks
the own cached frame at H+0x298 (`-1` means never), using the inclusive unsigned
`cachedFrame + frames >= currentFrame` comparison; success returns H+0x29C.
Otherwise it scans contained members in list order, then the registered H+0x170
object-ID set in ascending order, asking each live lookup for **four seconds**
of recent damage, regardless of the outer window. Released garrison members
remain in this registered set. The first matching source wins; no effectively
dead filter is added.

The cache writer is ordinary removal RW 0x87370B: RW 0x8737EE copies the removed
member's last-damager source (zero if no damage record; unchanged if no body),
and RW 0x873885 records the **current removal frame**, not the hit frame.
Constructor RW 0x87292F / 0x872960 initializes these to `-1` / zero.
Garrison release keeps the slot and does not write this cache. Both persistent
fields are included in the port's state hash: existing simulation pins can move
even at frame zero. No expected vectors are changed. The separate S-1620
forgotten-member-on-the-way transition remains an existing inference; this
does not claim to recover its absent-object writer.
