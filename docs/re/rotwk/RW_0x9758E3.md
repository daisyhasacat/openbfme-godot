# RW 0x9758E3 — lobby maximum-player query (S-3610)

## Owner and evidence

The caller RW 0x843245 passes `MpGameSetup +0x60`, the embedded map/scenario
preview controller. Its mode +0x1C is thus MpGameSetup +0x7C. BFME2's
`GameClient/GUI/MpGameSetupSlots.cpp` describes the corresponding AptMapPreview
subobject and mode. The original name of this particular method and the typed
scenario chain are not proven: use an address-named method rather than claiming
an original symbol. Evidence is the supplied target pack plus direct disassembly;
the PLAN rule 9 / S-001 modified-image caveat applies.

Offsets on this receiver:

| Offset | Proven meaning / limit |
| --- | --- |
| +0x18 | pointer to validated GameInfo holder, passed as this to RW 0x83FF11 |
| +0x1C | mode integer; only 1 takes the scenario branch |
| +0x68 | nullable context pointer for the scenario branch |
| context +0x29C | nullable intermediate pointer |
| intermediate +0x1C | nullable scenario/limits record |
| record +0x10 | maximum players (use as maximum is proven by start-check caller) |

**INFERENCE:** calling the last record a Living World scenario is supported by
mode 1 and the surrounding lobby's War-of-the-Ring behavior. No BFME2 class
member declaration matching all three pointer offsets was established; preserve
the offsets rather than borrowing an unrelated structure's member names.

    int mode = m_mode1C; // loaded BEFORE the holder call

There is **no fallback to map metadata in mode 1**, even if any scenario pointer
is missing. There is no clamp, range check, float operation or mutation in the
query itself. A negative / zero / greater-than-eight dword is returned unchanged.
The holder call has a side effect: RW 0x83FF11 calls its slot +4 with member +8,
clears +8 if AL is false, and returns +8. Its reachable body ends at 0x83FF28,
not the pack's 71-byte inventory extent. Verified target behavior agrees with
`Common/Rva0043DA65Getter.cpp`; the map's larger extent includes other functions.
Neither this pointer nor holder +0x18 is null-checked by retail.

Named callees: RW 0x627692 is GameInfo::getMap (BFME2 0x63E943,
`GameNetwork/GameInfoGetMap.cpp`); RW 0x703C91 is MapCache::findMap
(BFME2 0x7024BC, `GameClient/MapCacheFindMap.cpp`), lowercasing the map name
and returning a MapMetaData pointer or null. Return +0x20 is numPlayers; this is
also how the port's MapCacheEntry exposes it.

## Callers / when it runs

Pack call sites: RW 0x8417FF (within 0x84160F), RW 0x843245 (start check
0x8431B8), and RW 0x84465C / 0x84468C / 0x84476E / 0x8447D1 / 0x844950
(within 0x8445F2, lobby slot/setup updates; exact original method name unresolved).
The start check does a **signed** clamp to 8, refuses silently if maximum <=0,
then calls RW 0x97597F and refuses if minimum > maximum. Clamping belongs to
that caller, not either accessor.

## Port disposition

The non-strategic map lookup and start-check clamp already exist in
SkirmishGameSetup::checkStart. The engine does not yet have this scenario-owner
chain or a selected Living World scenario supplying the limits. Do not invent
scenario counts or a fixture-only setter and call it integration.

S-3610 remains open: its current **explicitly reported deviation** substitutes
map player count in strategic mode. Closing this part needs the selected scenario
model, missing-chain => 0 (never map fallback), and tests where scenario maximum
differs from map count, including missing holder/context/owner/record and caller
clamp/refusal. Existing `gamemodes1: the start check: ...` tests cover only the
map-count substitute, not recovered scenario behavior. No simulation change or
pinned-vector change in this recovery commit.
